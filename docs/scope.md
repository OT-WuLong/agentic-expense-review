本文将 `README.md` 中的产品边界收敛为 v1 的验收范围，只定义系统要解决的问题、参与角色、输入输出、职责归属和安全边界，不定义 API、数据结构、模型参数、规则阈值或部署方案。后续任务不得在未同步修改 `README.md` 与本文的情况下扩大或改变这些边界。

`README.md` 使用了泛化的“企业费用报销”表述；P00-T01 在此基础上将 v1 的顶层费用类型收敛为交通、住宿和餐饮，不在本任务中继续细分子类型。v1.1 同时将部署范围固定为单一公司，运行时请求和状态不引入租户字段，也不提供租户注册、切换、计费或跨租户隔离能力。

## 1. 产品定位

v1 是企业费用报销的预审辅助系统。系统接收报销申请和证明材料，围绕有效企业制度检索并复核证据，再结合确定性规则给出预审建议、理由和可定位证据，供申请人补充材料或财务审核员作出人工决定。

系统提供的是预审建议，不是企业的最终审批决定，也不执行支付、转账或正式审批动作。

本文冻结的是最终 v1 产品边界；Phase 1、Phase 2、Phase 3 只是逐步达到该边界的实施阶段，不能把 Phase 1 的 MVP 完成度等同于 v1 全部完成。

## 2. v1 业务范围

### 2.1 纳入的费用类型

v1 只覆盖以下三类费用：

| 费用类型 | v1 范围 |
| --- | --- |
| 交通 | 对交通费用申请、票据、适用制度证据和确定性规则进行预审 |
| 住宿 | 对住宿费用申请、票据、适用制度证据和确定性规则进行预审 |
| 餐饮 | 对餐饮费用申请、票据、适用制度证据和确定性规则进行预审 |

其他费用类型以及合同、采购、人事等业务不进入 v1 自动预审范围。

本阶段不冻结各费用类型的字段细目、金额标准和例外规则；这些内容必须在后续黄金案例、业务 Schema、制度样本和确定性规则任务中定义并验证。

### 2.2 预审能力

v1 覆盖以下业务能力：

1. 接收并标准化报销申请、附件、企业制度和授权的结构化业务数据。
2. 从数字文档或扫描件中抽取预审所需字段，并保留原文位置。
3. 根据申请动态拆解待验证问题，选择白名单内的只读检索工具，并在证据不足时有界补检。
4. 核对证据的覆盖度、适用时间、制度版本、引用完整性和冲突情况。
5. 使用确定性规则校验金额、日期、预算、权限、重复报销及其他可编码条件。
6. 输出三类预审建议之一，并提供原因、规则依据、引用证据和审核轨迹。
7. 在证据不足时允许有界补检或请求补充材料；仍无法解决、达到行动边界、高风险或需要业务裁量时，暂停并等待人工复核。

## 3. 用户角色

| 角色 | v1 职责 | 权限边界 |
| --- | --- | --- |
| 报销申请人 | 提交申请和附件；查看预审建议及补充材料要求 | 不能修改制度、规则、预审轨迹或人工审核结果 |
| 财务审核员 | 查看申请、证据、规则命中和风险原因；批准、修改或驳回预审建议 | 人工操作必须可追溯；不能借助 Agent 绕过权限和正式制度 |
| 规则管理员 | 维护制度版本；审核候选规则；处理规则冲突、发布与回滚 | LLM 生成的候选规则未经人工审核和发布不得参与正式判断 |
| 系统管理员 | 管理角色权限、模型配置、可配置阈值、日志保留和系统运行状态 | 不因系统管理权限改变财务制度的业务含义或伪造审核证据 |

## 4. 输入边界

v1 的业务输入分为四组：

| 输入 | 必要内容 | 边界 |
| --- | --- | --- |
| 报销申请 | 申请人、部门、费用类型、币种、金额、发生日期、说明 | 申请事实只能由授权用户提供或修正，Agent 不得自行改写 |
| 附件 | 发票、收据、行程单、审批截图及其他证明材料 | 附件内容是不可信数据，只能作为待抽取、检索和核验的材料 |
| 企业制度 | 报销政策、金额标准、部门预算、例外条款、生效与失效时间 | 只有已发布且在申请发生日期适用的制度或补充规则可作为正式依据 |
| 结构化数据 | 员工信息、预算余额、已报销记录、审批权限及必要的分类信息 | 只允许通过授权的只读查询获取，并执行角色、部门和文档范围校验 |

扫描件的 v1 目标是结构化字段抽取和可追溯的文本证据，不宣称原生图像向量检索能力。关键字段无法可靠识别时，系统不得猜测或补写。

## 5. 输出边界

### 5.1 唯一的三类预审建议

| 建议 | 适用条件 | 不适用情况 |
| --- | --- | --- |
| `PASS_RECOMMENDED` | 必要问题均有充分、有效且无冲突的可定位证据；关键字段一致；全部适用的确定性规则通过；不存在强制人工条件 | 任何必要证据缺失、规则失败、关键字段无法确认或高风险情形 |
| `REJECT_RECOMMENDED` | 可靠输入与有效制度已确认命中明确禁止且不存在人工裁量或例外空间的规则，或已确认关键事实相互矛盾并构成明确业务不通过 | 依赖故障、证据不足、事实尚不能确认，或可能适用例外审批的情形 |
| `HUMAN_REVIEW` | 证据不足或冲突、关键字段无法确认、风险较高、达到自主行动边界、金额超限，或命中其他强制人工条件 | 已满足自动建议通过条件，或命中不带强制人工条件的明确业务不通过规则 |

强制人工条件优先于明确硬规则不通过。因此金额超限在 v1 中进入 `HUMAN_REVIEW`；`REJECT_RECOMMENDED` 只用于未同时命中强制人工条件的明确业务不通过。本阶段不定义金额阈值或具体规则映射。

系统依赖失败、超时、权限失败和非法输入属于技术或请求状态，不得伪装成上述任何业务建议。补充材料请求是流程动作，不新增第四类预审建议；发出补充材料请求时可以尚未形成预审建议，只有实际转入人工复核时才使用 `HUMAN_REVIEW`。

### 5.2 每个预审结果必须包含

- 预审建议及结构化原因。
- 已确认的申请关键事实和不一致项。
- 命中的规则及其版本。
- 支持或反对建议的可追溯来源：文档证据包含引用片段、文档版本、适用时间和页码，可用时包含区域位置；结构化证据包含数据来源标识、查询类型和可重建的版本或快照信息，不伪造页码。
- 证据缺口、冲突、降级和风险原因。
- 可审计的 Agent 动作摘要、工具调用和停止原因。
- 发生人工复核时，人工操作前后的差异、操作者和理由。

系统不保存或展示模型的私有思维链，只记录理解预审过程所需的简短决策理由。

## 6. 三个 Agent 的唯一职责

三个 Agent 通过结构化状态协作，但各自只有一个决策层级的所有权。

| Agent | 唯一职责 | 允许产出 | 明确不负责 |
| --- | --- | --- | --- |
| Supervisor Agent | 维护全局预审目标，并在具有业务意义的阶段边界分派下一项任务或选择异常处理方向 | 面向下游的阶段任务、约束和结构化路由意图 | 不执行检索；不判定单条证据是否充分；不执行确定性规则；不作最终审批决定 |
| Retrieval Agent | 将当前检索目标拆成可验证子问题，并规划白名单内只读工具的选择、参数和补检路径 | 结构化检索计划、子问题、查询参数和检索执行请求 | 不修改申请事实；不裁定证据充分性；不提出补材料或升级人工建议；不执行规则；不输出预审建议或最终审批决定 |
| Evidence Reviewer Agent | 复核候选证据能否覆盖各子问题，并识别适用性、时效性、引用缺口、冲突和语义漂移 | 带 Evidence ID 的覆盖结论、证据缺口，以及充分、补检、补材料或升级人工的建议 | 不亲自检索；不改写申请事实或正式制度；不执行确定性规则；不输出最终预审或审批决定 |

职责交接关系为：Supervisor 下达阶段目标，Retrieval Agent 规划并请求检索，非 Agent 工具返回候选证据，Evidence Reviewer 复核证据并反馈缺口，Supervisor 再根据结构化反馈决定下一阶段。Retrieval Agent 与 Evidence Reviewer 可以围绕缺口循环，但不能互相代替。

以下高风险职责明确不属于任何 Agent：

- 文档解析器负责字段抽取、归一化和来源定位。
- 检索工具负责执行查询、过滤、融合和排序，不自行决定业务结论。
- Rule Validator 以确定性代码和受控数据执行金额、日期、预算、权限及重复报销等规则。
- Guardrail Router 以确定性条件执行权限、行动边界、风险优先级和三类建议路由。
- 财务审核员作出需要人工裁量的决定；真实企业系统仍拥有最终审批权。

## 7. 风险边界

### 7.1 Agent 与 LLM 权限

- Agent 只能读取完成当前预审所必需的数据，并只能调用白名单内、参数经过校验的只读工具。
- Agent 不得发起任意 URL、SQL、Shell、写库、支付、审批或权限提升操作。
- Agent 不得修改申请金额、日期、部门等事实，不得根据常识补写企业制度或伪造 Evidence ID。
- LLM 可以辅助文档结构化、检索规划和证据语义复核，但不能覆盖确定性规则或人工决定。
- 自主检索必须有明确预算和停止条件；超过边界后转入人工处理，不能无限循环。

### 7.2 决策与证据

- 没有可定位证据时，不生成确定性的合规结论。
- 在申请发生日期有效且已发布的制度（包括当时有效的历史版本）和已发布补充规则是正式依据；历史案例只能参考，不能覆盖制度。
- 候选规则默认不可用于自动判断，必须由规则管理员审核、测试并发布。
- 金额、日期、预算、权限、重复报销等可编码判断必须由确定性规则执行。
- 不使用未经独立验证的模型自报置信度作为自动通过依据。

### 7.3 失败、人工与审计

- 技术错误、证据不足和业务不通过必须使用不同状态和后续路径。
- 证据不足、规则冲突、关键字段不确定或高风险请求必须能够暂停并由财务审核员处理。
- 每个业务结论必须可回溯到输入字段、制度证据、规则版本和运行轨迹。
- 用户、角色、部门和文档权限必须贯穿业务查询、证据访问和人工操作。
- 日志和轨迹只保留完成审计所需的信息，并对身份、账户、电话、发票等敏感字段脱敏。
- 写库、通知、案例沉淀和人工操作等副作用必须具备幂等性，恢复执行不得产生重复结果。

## 8. v1 非目标

v1 明确不包含：

1. 执行真实支付、转账或正式企业审批。
2. 覆盖交通、住宿、餐饮之外的其他费用类型，或扩展到合同、采购、人事等审批领域。
3. 允许 LLM 自动创建、发布、覆盖或绕过正式规则。
4. 让历史案例或统计画像拥有高于当前有效制度的决策权。
5. 将 OCR/VLM 后的文本检索描述为原生图像向量检索。
6. 使用未经评测的模型自报置信度触发自动通过。
7. 将固定查询改写次数、固定路由或普通函数包装成自主 Agent，而不记录和评测真实动作轨迹。
8. 让任何 Agent 执行确定性审批规则、最终人工审批或外部写操作。
9. 在取得真实评测结果前承诺任务成功率、延迟、成本、安全性或人工复核率。
10. 为 v1 引入 Kubernetes、微服务拆分、通用审批规则 DSL 或多模型供应商路由。
11. 为多个公司提供租户生命周期、租户切换、租户计费或跨租户隔离；这些 SaaS 能力留待 MVP 之后评估。

## 9. 冻结范围验收

P00-T01 的范围冻结满足以下条件：

- 费用类型只有交通、住宿、餐饮三类。
- 业务预审建议只有 `PASS_RECOMMENDED`、`REJECT_RECOMMENDED`、`HUMAN_REVIEW` 三类。
- 报销申请人、财务审核员、规则管理员、系统管理员的职责和权限边界明确。
- 四类业务输入和每个结果的必要输出明确。
- Supervisor、Retrieval Agent、Evidence Reviewer 的职责互斥，且没有取得规则执行权或最终审批权。
- 风险边界覆盖最小权限、证据优先、确定性决策、人工兜底、角色／部门／文档授权、隐私和审计。
- 非目标明确排除真实审批执行、范围外业务、规则自治、原生图像向量检索、多租户 SaaS 和未经验证的效果承诺。
- 文档中的产品边界均有明确结论，且不包含空白参数或未经评测的效果数字。

后续如果实验表明三 Agent 划分没有可测收益，必须先回到范围与架构决策，更新 `README.md`、本文及受影响的任务卡，再实施角色合并；不得在下游任务中静默改变本次冻结的职责边界。
