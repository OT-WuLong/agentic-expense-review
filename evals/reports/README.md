# Evaluation report retention

- `golden_trajectories.latest.json` always records the most recent live attempt, including dependency failures.
- `golden_trajectories.last_pass.json` is updated only after all frozen golden cases pass; it may be absent before the first successful run of the current contract.
- Targeted `--case-id` runs are marked `PARTIAL` and never update `last_pass`, even when merged display results happen to show 3/3.
- `supervisor_challenge_smoke.json` is a deterministic Fake-model check for challenge preservation, query-rewrite counting, canonical Supervisor stops, Reviewer immutability, and both Guardrail violation paths; it is not a real-model quality score.
- `p09_recovery.json` is a PostgreSQL infrastructure smoke with a Fake model and Stub tool. It measures checkpoint restart, bounded persistence retry, projection consistency, and duplicate side effects from event counts; it is not evidence that a live golden trajectory completed human review.
- `hybrid_ablation.json` is the live P11 validation comparison across Milvus BM25, Qwen Sparse, Qwen Dense, Hybrid+RRF, and Hybrid+RRF+`qwen3.7-text-rerank`. It records end-to-end latency, route candidates, token usage, degradation, filter violations, and one Milvus resource snapshot; the frozen test split was not opened.
- `p12_memory_smoke.json` checks real PostgreSQL case persistence, department filtering, and candidate approval/publication/rollback with a Fake draft model.
- `p12_case_memory_ablation.json` compares `deepseek-flash` on three validation samples with/without `case_search` after preserving their original request IDs. Both modes reached 3/3 task success and 1/3 human intervention, with zero system errors. The temporary dev-seeded case was ineligible for all three samples under the department/date filter; no case-search call or hit occurred, so the benefit of a relevant memory hit is `NOT_MEASURED`. Frozen test samples were untouched.
- `p13_security.json` checks configured session/RBAC/CSRF, PostgreSQL and live Milvus scope, read-only tool schema, forged citations, long excerpts, safe Vue rendering, and two live DeepSeek attack/benign pairs from dev/validation. Its 0/22 attack successes and 0/8 false blocks are small-sample boundary results, not a general jailbreak claim; frozen test was not executed.
- `agentic_ablation_qwen_v4.json` plus `agentic_ablation_qwen_v4_raw/` compare five live validation variants with all three raw predictions per variant. Fixed double-query retrieval reached 2/3 strict tasks versus 1/3 for full multi-Agent; no Agentic quality uplift is claimed. Earlier failed Qwen and old-prompt DeepSeek attempts are retained separately rather than merged into the current comparison.
- `p14_frontend_e2e.json` joins a same-run 4/4 production-build Playwright pass with persisted PostgreSQL audit events for A/B/C. It records zero duplicate side effects and per-case machine time to finalization or human interrupt; public golden cases are not a statistical P95 sample.
- `p14_recovery.json` repeats the P09 checkpoint/idempotency smoke with a Fake model and Stub tool. It is infrastructure recovery evidence, not a live model fault-injection rate.
- `p14_test_once/` is the only frozen-test execution for dataset 1.2.0 on clean commit `080fe29`. It is `INVALID_RUN`: the security evaluator crashed on a structured payload, while non-golden workflow task success was 0/3. Keep the raw failure output; do not treat its partial retrieval metrics as an overall pass or rerun this frozen split after a code change. See `p14_test_postmortem.md`.
- `p14_holdout_v1_3_preflight.md` records the replacement `1.3.0` test design, its public-policy references, repaired rule catalog, DeepSeek validation result, and non-blind limitation. `p14_validation_v1_3_deepseek/` holds the selected full validation run; transient Qwen failure attempts remain local under ignored `tmp/` and are not merged into the selected score.
- `p14_test_v1_3_once/` is the only read-only test execution for the author-created synthetic `1.3.0` holdout, on clean commit `d9bfee4`. All ten pre-frozen thresholds passed, but strict task success and exact rule match were 2/3; the missing-headcount case requested documents before the rule validator ran. `p14_test_v1_3_interpretation.md` gives the case-level explanation. This is a versioned regression, not an independent external blind test or a population-quality estimate. The no-answer accuracy remains `NOT_MEASURED`.
- `p15_deployment_smoke.md` records local Docker build/bootstrap, same-origin SPA/API routing, HTTPS/SSE and the three targeted synthetic demo approvals including C's human resume. It also preserves two failed B attempts and their distinct causes; it is not a public deployment or load-test report.
- `validation_1_4_active_qwen_postfix_full.json` is one complete 26-case synthetic validation run using `qwen3.8-flash` and the active single-company policy catalog after the routing fixes: recommendation match 24/26 (92.3%), strict task success 14/26 (53.8%), and one TLS system error included in both denominators. Six newly authored invoice cases passed strictly. This is not frozen test or an external accuracy claim.
- `validation_1_5_active_qwen_full.json` and its `.md` interpretation are one complete 60-case run on the unfrozen 1.5.0 validation draft: recommendation match 55/60, strict task success 33/60, with five system errors included. The later 1.5.1 draft corrects two unreachable meal evidence labels; the two runs remain separate. Workflow reports from 1.5.1 use schema v2 to keep Agent stop reasons separate from final rule decision reasons.
- `validation_1_5_1_active_qwen_full.json` and its `.md` interpretation are the historical complete 60-case run on corrected 1.5.1 gold: recommendation match 57/60, strict success 40/60, one system error and one false auto-pass. The schema-v2 diagnostic without Agent stop matching is 49/60, not a replacement for strict success.
- `validation_1_5_2_active_qwen_full.json` and its `.md` interpretation are the new complete 60-case run after invoice-headcount and explicit-commute routing fixes: recommendation match 59/60, strict success 37/60, zero false auto-passes among 37 non-pass cases, and one system error. Seven meal-rule gold outcomes changed in this version; do not combine or directly compare strict scores across the two runs. Two separate raw-PDF HTTP uploads also checked the repaired business decisions, but are not included in the 60-case score.
- `validation_1_5_2_active_deepseek_postfix_full.json` and its `.md` interpretation are a separate complete 60-case run on the same 1.5.2 gold after Retrieval/Reviewer prompt and citation changes, using `deepseek-flash`: recommendation match 60/60, strict success 51/60, zero false auto-passes among 37 non-pass cases, and zero system errors. The model also changed from the prior Qwen run, so the score delta is not a controlled ablation. Three raw-PDF HTTP upload paths passed separately; browser file-selection interaction was not verified.
- `single_vs_multi_dense_1_5_2_deepseek_20261002.json`, its raw predictions and `_interpretation.md` compare the same 60 synthetic validation rows using a unified-prompt, single-round Agent baseline against the current multi-Agent workflow. Suggestion match is 57/60 vs 59/60, architecture-neutral business success 54/60 vs 56/60, and contractual strict success 47/60 vs 50/60; false auto-pass is 0/37 in both. One baseline model timeout is included. All multi-Agent cases used one retrieval round, so no iterative-retrieval benefit is established; M10 has a policy/location requirement vs gold-boundary question, with the original grade retained.

In `p13_security.json`, `blocked` means the attack objective failed, not necessarily that the request was rejected: the Milvus scope case returned five authorized documents. `security_denial_audit_events` counts actual denial events, not attack cases; the anonymous `GET /session` denial is intentionally excluded and the cookie-flags check does not issue a denial request. The historical P10 frontend quality report retains its original 128/137 backend-test count. On the P13 checkout, `uv run python -m pytest -q` passed 138 tests in 16.82 seconds on 2026-09-25; a previously reported 300-second stall was not reproduced in two current full runs.

The earlier P07 live `3/3` report remains available in Git commit `293ae3f`, but it predates the P08 Supervisor challenge contract and must not be presented as evidence for the upgraded Supervisor.

The current `latest` report is a targeted `PARTIAL` rerun of case B merged with the prior A/C records. B now passes and retrieves its required lodging-limit evidence group, but the merged 3/3 summary is not a full current run. `last_pass` therefore remains the earlier full pass and is not evidence for the newest uncommitted control-flow changes.
